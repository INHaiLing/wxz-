# 后端开源调研与技术选型

调研日期：2026-10-02

文档状态：技术方案建议；经营与支付入口规则待需求问卷确认

适用项目：专升本语文微信原生小程序、Web 管理后台

## 1. 选型结论

推荐 **Python 3.13 + Django 5.2 LTS 最新安全补丁 + Django REST Framework（DRF）+ Django Admin / Unfold + django-import-export + PostgreSQL**，首版采用模块化单体部署。

推荐理由来自本项目的工作重心：维护分类、篇目和题目，批量导入题库，管理用户权益、订单及激活码。这些功能需要较多管理表单、权限控制和数据库事务。Django 自带管理后台与 ORM，Unfold 改善管理界面，导入组件提供预览与校验基础，可减少独立 Web 前端的建设和维护。现有原生小程序继续通过 HTTP API 获取数据，不需要因后端使用 Python 而更换前端框架。

这属于针对当前需求的工程判断，不是对 Python 与 Node.js 性能的普遍排名。若后续形成专职 TypeScript 团队、后台需要大量复杂交互，Node.js 方案的取舍可重新评估。

版本采用以下规则：Python 固定 3.13 系列；Django 固定 5.2 LTS 系列并安装实施时最新安全补丁；其余依赖在兼容性验证后锁定准确版本。Django 官方当前列明 5.2 LTS 扩展支持至 **2028 年 4 月**。[Django 支持周期](https://www.djangoproject.com/download/)

## 2. 需求与复用目标

| 项目需要 | 复用目标 | 仍需开发的项目规则 |
|---|---|---|
| 题库维护 | 管理列表、搜索、表单、导入导出 | 文学分类、文言篇目、题型、题干与答案校验、发布版本 |
| Web 管理后台 | 管理员登录、用户组、模型权限、导航 | 题库编辑、订单只读详情、激活码批次操作和经营数据 |
| 支付与开通权益 | 官方支付协议及通用 HTTP / 签名能力 | 订单、支付渠道适配、验证、发放权益、退款与补偿 |
| 激活码 | 安全随机数、数据库约束、事务能力 | 批量生成、一次性核销、期限、作废、追踪与经营规则 |
| 小程序接入 | REST API、序列化、鉴权基础 | 微信身份绑定、付费内容校验、学习记录同步 |

调研没有发现经本次验证、可以不做业务开发就完整覆盖本项目的成品系统。可直接复用的是框架和通用模块；题库发布、权益、支付以及激活规则需要独立设计和实现。

## 3. 五个候选对比

### 3.1 Django + DRF + Unfold：推荐后台基础

- **可复用能力**：Django Admin 提供模型管理和权限基础；DRF 提供 API；Unfold 提供导航、筛选、表单、批量操作和自定义后台页面组件，可集成 django-import-export。
- **许可证**：Django 和 DRF 为 BSD-3-Clause；Unfold 为 MIT。使用时保留适用的版权与许可文件。
- **维护证据**：Unfold 变更日志显示 **0.108.0 于 2026-09-24 发布**；该版本项目声明 Python `>=3.12,<4.0`、Django `>=5.2`，与本方案一致。
- **适配代价**：需要建立业务模型、管理表单与 API；发布、核销和退款等流程需要定制管理操作。后台以内部运营效率为目标，复杂所见即所得题目编辑器不能视为自动具备。
- **判断**：首版维护成本较低；直接使用组件，不需要复制一个包含大量无关业务的完整平台。

来源：[Django Admin 官方文档](https://docs.djangoproject.com/en/5.2/ref/contrib/admin/)、[Django 仓库与许可证](https://github.com/django/django)、[DRF 许可证](https://github.com/encode/django-rest-framework/blob/master/LICENSE.md)、[Unfold 原仓库](https://github.com/unfoldadmin/django-unfold)、[Unfold 变更日志](https://github.com/unfoldadmin/django-unfold/blob/main/CHANGELOG.md)、[Unfold 版本兼容声明](https://github.com/unfoldadmin/django-unfold/blob/main/pyproject.toml)。

### 3.2 django-import-export：推荐题库导入配套模块

- **可复用能力**：CSV / XLSX 等格式导入导出、管理后台导入预览、逐行差异、批量处理、可扩展校验。
- **许可证**：BSD-2-Clause。
- **维护证据**：官方变更日志列明 **4.4.1 于 2026-05-05 发布**；此前 4.3.6 已加入 Django 5.2 支持。Unfold 当前开发依赖也包含 4.4.1，可作为组合兼容的参考，不能替代本项目集成测试。
- **适配代价**：需要定义题库模板、稳定题号、分类及篇目引用、题干占位符与答案数量校验，并明确失败处理和发布流程。文件解析成功不等于内容可以直接发布。
- **判断**：作为 Django 方案的配套模块使用，不单独构成后端系统。首版优先限定 XLSX / CSV，避免一次开放所有解析格式。

来源：[原仓库与许可证](https://github.com/django-import-export/django-import-export)、[官方变更日志](https://django-import-export.readthedocs.io/en/latest/changelog.html)、[安装与格式依赖](https://github.com/django-import-export/django-import-export/blob/main/docs/installation.rst)。

### 3.3 Django-Vue3-Admin：具备完整后台，但升级与裁剪较多

- **可复用能力**：Vue3 后台、动态菜单、角色、按钮和字段权限、文件管理、操作日志；后端采用 Django + DRF。
- **许可证**：目标 GitHub 仓库 `LICENSE` 为 Apache-2.0。社区插件、商业服务和附加模块需要分别核实，不能把仓库许可扩展到所有插件。
- **维护证据**：GitHub `master` 提交订阅最后记录为 **2025-09-19**；截至本次调研，`backend/requirements.txt` 仍固定 Django **4.2.14**、DRF **3.15.2**。项目说明主推 Gitee，GitHub 日期仅代表该镜像可核实的证据，不代表整个项目停止维护。
- **适配代价**：需把旧依赖升级到仍受支持的版本、验证权限链路，并维护 Python 和 Vue 两套工程；组织部门、区域等当前不需要的模块也需裁剪。
- **判断**：若未来明确需要较复杂的独立后台交互，可作为参考；本项目首版不直接复制整套平台。

来源：[原仓库](https://github.com/huge-dream/django-vue3-admin)、[实际许可证](https://github.com/huge-dream/django-vue3-admin/blob/master/LICENSE)、[后端依赖](https://github.com/huge-dream/django-vue3-admin/blob/master/backend/requirements.txt)、[GitHub 提交订阅](https://github.com/huge-dream/django-vue3-admin/commits/master.atom)。

补充：旧版 [django-vue-admin（Vue2）](https://github.com/liqianglog/django-vue-admin) 的 README 有 MIT 徽章，但 [实际 LICENSE](https://github.com/liqianglog/django-vue-admin/blob/master/LICENSE) 为 Apache-2.0；应以准备采用的准确版本许可文件为依据。其 GitHub 提交订阅最后记录为 2023-09-18，不选作本项目新工程基础。

### 3.4 NestJS + AdminJS：Node.js 可行方案，组合集成需要额外处理

- **可复用能力**：NestJS 提供后端模块组织；AdminJS 根据数据库模型生成管理界面，支持 ORM 适配和自定义操作。
- **许可证**：NestJS、AdminJS 均为 MIT。
- **维护证据**：AdminJS 发布页最新公开版本为 **v7.8.17，2025-07-15**。这是发行记录，不能单凭发行间隔断言项目停止维护。
- **适配代价**：AdminJS v7 为 ESM-only；官方 Nest 集成文档说明 CommonJS 工程需要动态导入等处理，Nest 插件仅支持 Express。题库导入预览、业务权限及中文后台细节仍需补齐。
- **判断**：适合已有 Node.js 服务再补管理界面的团队；当前从零构建时，没有比 Django 组合更明确的成本优势。

来源：[NestJS 许可证](https://github.com/nestjs/nest/blob/master/LICENSE)、[AdminJS 原仓库](https://github.com/SoftwareBrothers/adminjs)、[AdminJS 许可证](https://github.com/SoftwareBrothers/adminjs/blob/master/LICENSE.md)、[AdminJS 发布记录](https://github.com/SoftwareBrothers/adminjs/releases)、[官方 Nest 集成限制](https://docs.adminjs.co/installation/plugins/nest)。

### 3.5 Cool Admin Midway + Cool Admin Vue：Node.js 备选

- **可复用能力**：Node.js / TypeScript / TypeORM 后端，Vue3 管理界面，CRUD、权限、模块和插件机制。
- **许可证**：调研的后端与前端 `8.x` 分支均为 MIT。
- **维护证据**：后端 `8.x` 提交订阅最后记录为 **2026-07-17**；项目提供持续维护的中文说明和模块化方案。
- **适配代价**：需要理解框架封装、权限及插件约定，维护独立前端；题库发布、权益、支付和激活码仍需开发。仓库示例包含自动建表配置，生产应改用明确的迁移流程。
- **判断**：若选择 Node.js，优先验证这个候选。其 README 提到支付插件，只能证明有插件扩展方向，不能据此认定插件免费、官方、支持 xpay 或已经满足本项目上线要求。

来源：[后端原仓库](https://github.com/cool-team-official/cool-admin-midway)、[后端许可证](https://github.com/cool-team-official/cool-admin-midway/blob/8.x/LICENSE)、[前端许可证](https://github.com/cool-team-official/cool-admin-vue/blob/8.x/LICENSE)、[后端提交订阅](https://github.com/cool-team-official/cool-admin-midway/commits/8.x.atom)。

## 4. 推荐架构与复用边界

### 4.1 模块化单体

```text
原生微信小程序 ── 小程序 API ──┐
                             │
Web 管理后台 ── Django Admin ─┼── 共享业务服务 ── PostgreSQL
                             │
微信虚拟支付 ── 通知/查单适配 ─┘
```

首版一个 Django 工程承载管理后台和小程序 API，部署为一个应用服务。内部按账号、内容、学习记录、商品权益、订单支付、激活码和审计分模块。数据库作为订单、核销和权益的一致性依据；不因“模块化”拆成多套服务。

后台使用 Django Admin + Unfold，首版不额外建设 Vue / React 管理工程。部署环境使用 PostgreSQL；测试支付、核销并发等事务行为时同样使用 PostgreSQL。后续确有异步任务需求时再增加队列，不将 Redis、Celery 或微服务作为首版必选项。

### 4.2 直接复用

- Django 账号、用户组与管理员权限基础，管理表单、过滤、分页、ORM 和数据库迁移。
- DRF 的请求校验、序列化、API 视图及鉴权扩展点。
- Unfold 的后台主题、导航和管理页面组件。
- django-import-export 的解析、预览及行级结果展示；采用项目专属资源定义和校验。

### 4.3 项目必须定制

- **题库内容**：保持稳定题号，建立分类和篇目关联；校验题型、题干和答案；区分编辑草稿与已发布内容，避免导入立即污染线上题库。
- **访问权益**：统一表达用户能访问的题库范围和期限；付费内容由服务端校验。正式付费题库不能继续随小程序安装包完整下发。
- **支付订单**：创建订单、渠道适配、通知校验、查单、重复通知幂等、异常补偿、退款及权益处理。
- **激活码**：批次生成、有效期、核销次数、绑定用户、作废和导出记录；数据库事务保证并发核销只产生一次有效发放。
- **共享发放服务**：支付确认与激活成功进入同一个权益服务，保留各自来源；不得通过随意修改订单状态来冒充真实付款。
- **审计**：记录题库发布、权益变更、激活码导出与作废等关键动作；管理后台可执行的操作按角色授权。

这些是建议的实现边界，具体商品期限、试用范围、重复购买、退款和核销规则以 RRD 与用户问卷答复为准。

## 5. 支付选型的重要更新

本项目销售的是小程序中的题库访问、学习功能或会员权益，按虚拟内容场景设计。支付技术路线采用 **微信小程序官方 xpay 虚拟支付**，后续依据主体、类目、实际开通能力及业务模式完成接入验证。[微信官方小程序虚拟支付文档](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment.html)

普通微信支付 API v3 模块（例如第三方 `wechatpayv3` 包）与小程序 xpay 虚拟支付属于不同接入能力。**支持普通微信支付不代表支持 xpay**；不得仅因包名含“微信支付”就把它写入本项目的已验证依赖。任何支付 SDK 候选都需要进一步核查：准确版本、许可证、xpay 接口覆盖、签名、通知处理、查单、退款和维护情况。没有合适 SDK 时，使用受控适配层调用官方协议，测试后再确定依赖。

扫码是用户入口，不能仅凭“扫码支付”四个字确定使用 Native 支付接口。需要结合问卷 **Q04** 确认：二维码展示在哪里、谁扫码、扫码后进入哪个端、权益绑定给哪个用户，再决定官方支持的完整链路。不得预设使用个人收款码配合截图人工开通作为标准支付流程。

激活码的经营来源与发放人员见问卷 **Q08**；使用次数、兑换有效期、机构标记与原码导出见 **Q09**；转移及重复权益处理见 **Q10**；适用商品范围见 **Q01**。激活码本身是权益核销凭证，不自动构成对平台交易要求的豁免；是否允许特定入口和经营方式应按已确认场景核验。

本调研不确定平台费率、可开通主体、iOS 具体能力或审批结果，也不把网上第三方教程当作本项目已获准开通的证明。上述项目应在接入前依据官方后台和文档确认。

## 6. 实施前验证清单

| 验证项 | 通过条件 |
|---|---|
| 依赖组合 | Python 3.13、Django 5.2 最新安全补丁、DRF、Unfold、导入模块可安装运行，并锁定实际版本 |
| 管理后台 | 管理员能按权限维护题库；普通内容编辑不能执行支付退款或批量导出激活码 |
| 题库导入 | 合法文件可预览并导入；重复题号、无效篇目、缺答案和占位符错误有清晰结果；未发布内容不对学生开放 |
| 权益与内容 | 未登录、无权益、过期用户不能读取付费内容；购买或核销成功后获得对应范围和期限 |
| 支付适配 | 使用已确认的 xpay 场景完成下单、可信支付确认、查单、异常及退款验证；前端“成功”回调不单独触发发货 |
| 激活并发 | 同一码并发兑换不能重复发放；过期、已用和作废码按业务规则拒绝并留记录 |
| 小程序兼容 | 原生页面和现有学习交互可接入 API；登录、网络错误及题目下架时有明确状态 |
| 发布运维 | 具备环境配置、数据库迁移、备份恢复、服务健康检查和支付异常排查方式 |

本次交付是调研与选型文档，未下载或部署候选项目，未完成支付联调，也未将第三方维护记录视为安全审计结论。后续开发以用户答复后的 RRD 为准。
