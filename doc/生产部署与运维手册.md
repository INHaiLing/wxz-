# 后端部署与运维

适用 Linux、Python 3.14、PostgreSQL 16、Nginx 与 Gunicorn。本文是可运行模板，当前没有实际服务器／域名，未完成公网验收。

## 初始化

建议版本目录 `/srv/chinese-study/releases/<commit>/`，`current` 指向已验收版本；代码由部署专用账号获取，运行账号 `chinese-study` 不可修改代码。数据库只允许本机／指定内网应用连接。独立创建数据库、用户及强密码；CI 的一次性密码不得用于生产。

```bash
python3.14 -m venv /srv/chinese-study/venv
/srv/chinese-study/venv/bin/pip install -r backend/requirements-production.txt
```

将 `backend/deploy/production.env.example` 的配置通过受控方式保存至 `/etc/chinese-study/backend.env`，文件仅 root 与运行账号可读（640），目录 750。替换全部占位值，填写明确域名；`STUDENT_SESSION_ENCRYPTION_KEYS` 为 Fernet 密钥，单独加密备份。不要复制开发 `.env`。未准备支付时保持渠道关闭。生产设置要求 PostgreSQL、关闭 DEBUG、明确 HTTPS 和秘密配置；运行以下命令时须将环境文件安全加载到进程环境。

```bash
cd /srv/chinese-study/current/backend
export DJANGO_SETTINGS_MODULE=config.production_settings
/srv/chinese-study/venv/bin/python manage.py check --deploy --fail-level WARNING
/srv/chinese-study/venv/bin/python manage.py migrate --plan
/srv/chinese-study/venv/bin/python manage.py migrate
/srv/chinese-study/venv/bin/python manage.py setup_roles
/srv/chinese-study/venv/bin/python manage.py setup_business_roles
/srv/chinese-study/venv/bin/python manage.py seed_product
/srv/chinese-study/venv/bin/python manage.py createsuperuser
/srv/chinese-study/venv/bin/python manage.py collectstatic --noinput
```

`seed_product` 保留已有商品和价格；没有默认管理员。真实题库通过后台按 XLSX 模板预检、确认导入后发布；`seed_demo` 仅测试环境使用。初始化权限组按角色分配，撤权、发码、商品同步等高影响权限需要单独授权。新模块权限追加以模块说明为准，不把所有操作权限授予普通查看人员。

`setup_business_roles` 创建缺失的六个组：业务查看（业务只读，包含支付事件）、学员启停（专用 StudentAccount 查看／启停）、商品运营（改价、平台同步）、激活码管理（生成、领取、启禁／作废）、权益撤销（预览与审计后撤销指定来源）、支付核查（订单／事件／任务／开通占位查看及受控重新调度补偿任务）。学员启停组不含 `change_user`，不能改超级管理员、账户权限或后台角色；不向业务人员授通用账户编辑权限。支付核查不授直接改订单或直接发放权益权限，重新调度仍由平台确认与状态机处理。题库编辑、发布沿用 `setup_roles` 分离组。

两项命令只创建缺少的组，不给已有用户自动分组、不修改已有组、不扩大已有权限。缺少真实 app／model／codename 的业务权限时整批失败，应先迁移完整模块。新增模块权限需管理者审查后手工分配，重复初始化不会替已有角色追加权限。后台工作人员的账号及 is_staff 由可信账户管理员单独建立，初始权限为空；按工作职责显式加入所需组。

将收集的静态资源复制到 Nginx 模板指定的 `/srv/chinese-study/static/`，或调整模板路径；静态文件可读，私有导入／备份目录不提供 HTTP 服务。填写 `nginx.conf.example` 域名与证书，运行 `nginx -t`。TLS 证书配置好后，启用示例 systemd 服务；Gunicorn 只绑定 127.0.0.1，防火墙关闭 8000 对外访问，Nginx 始终重写代理头。未知 Host 不代理。检查 `/healthz` 和仅内部可访问的 `/readyz`，管理员登录与静态资源均可用。

本项目落实了 [Django 部署检查](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/) 中生产设置检查、HTTPS 和静态资源的要求；启动检查不能替代真实环境验收。

HSTS 只覆盖本服务，默认不承诺全部子域 HTTPS、不申请浏览器 preload；对应可选提示 W005/W021 单独注明并静默，其他部署提示仍阻止启动。甲方核对所有子域与长期 TLS 策略后可自行启用，避免影响其他业务域名。

## 数据库备份与恢复

备份包含账户、令牌摘要、题库、业务历史和加密微信会话，按敏感数据管理。使用仅运行账号可访问的目录，不向公开 Git／Web／普通网盘上传。生产存储应加密、异机备份；备份数据库时另行备份匹配的加密密钥及安全配置。工具不会导出原激活码，也不会打印密码。Linux 文件权限为 600，新建目录为 700；Windows 开发环境还需操作系统 ACL。

```bash
python manage.py backup_database --output /var/lib/chinese-study/backups/20261002T120000.dump
```

SQLite 使用一致快照；PostgreSQL 使用 [pg_dump custom 格式](https://www.postgresql.org/docs/16/app-pgdump.html)。生产安装 PostgreSQL 16 客户端，工具版本不能旧于服务器。命令拒绝覆盖已有备份，不自动删除旧备份。暂定每天备份、保留最近 30 天和每月备份；具体保留策略与存储由运营确定，不冒充已启用的定时任务。

恢复操作先停写并保留现库快照。PostgreSQL 预先创建另一个空数据库（如 `chinese_study_restore`），SQLite 指定不存在的新文件：

```bash
python manage.py restore_database --input /var/lib/chinese-study/backups/20261002T120000.dump --target chinese_study_restore
```

工具拒绝当前配置库或非空目标；PostgreSQL 使用 [pg_restore 单事务](https://www.postgresql.org/docs/16/app-pgrestore.html)，失败不会留下部分导入。恢复先在隔离环境启动同一提交，核对迁移、题库发布数量、权益来源／撤销、订单及补偿记录，验证密钥能解密旧会话。确认后再切换数据库配置、重启应用和补偿服务。恢复期间禁止两个应用同时处理同一组支付事件；对照平台订单补回备份时点后的交易。不把数据库备份当作自动撤销真实付款的依据。

## 从 SQLite 转 PostgreSQL

正式运营前完成一次演练：停止写入，保留 SQLite 快照，在新 PostgreSQL 库完成迁移；通过受控 `dumpdata --natural-foreign --exclude contenttypes --exclude auth.permission` 导出业务数据，并 `loaddata` 到新库，核对所有数量、稳定题目 ID、权限组和发布引用。导出文件包含秘密密文，禁止提交。若已有真实订单，必须全程停写、核对开通占位／事件任务；禁止合并两个已对外交易的数据集。正式迁移前按实际模块版本重复完整流程及接口测试，本手册不声称现有开发库已迁移生产。

CI 通过 `python backend/scripts/verify_database_transfer.py` 验证上述流程，要求显式 TEST_DB_NAME／USER／PASSWORD／HOST（PORT 可选）指向一次性 PostgreSQL 16 环境、测试角色具有创建库权限。该脚本始终自己建立临时 SQLite 源、私有快照和导出文件，生成测试学员、两版发布／未发布草稿、固定练习与学习状态，以及有效／撤销永久来源；不会读取现有开发 SQLite 文件。目标只使用脚本新建的 `transfer_check_<随机 UUID>` 空库，不提供自选生产目标参数。

演练实际执行目标迁移与导入，逐条核对完整业务导出、自然权限关系、稳定题目与修订引用、会话密文可解密、永久权益与撤销审计；检查两端数据库约束、源／快照完整性和 SHA256 不变。所有导出均只写临时私有目录，Linux 目录 700、文件 600；脚本结束清理私有文件及亲自创建的随机目标库，清理前再次检查所属集合／命名／当前配置库排除条件。该自动化证据只证明测试数据演练，不能当作真实生产数据已迁移的证明。

## 发布与回退

每次上线固定提交与完整依赖锁：先备份、`migrate --plan`、在隔离恢复库跑业务验收，再部署、迁移、收集静态资源与重启。有破坏性迁移时先设计数据兼容升级，不能直接按旧提交回退。无模式变更可切换旧提交；已经迁移的数据库应按经测试的前向修复或独立恢复方案处理，保留平台最新付款／退款记录再补偿。原版本标签保留；仅真实验收完成后创建 1.0.0。

## 日志、监控与任务

生产应用输出单行 JSON：requestId、已匹配路由名、状态、耗时；不记录 raw URL、query、正文、Authorization、Cookie、原码、微信密钥或完整异常值。日志通过 journal 收集，限制访问与保留；根据 5xx、503、超时率、数据库容量、备份年龄、支付待核查与任务重试积压建立报警。报警收件方与监控平台尚未提供，不能声称已开通通知。操作审计在数据库只读保留，定位问题以 requestId 与本地订单 ID 核对。

示例 Nginx 关闭原始请求 access/error 日志，避免代理失败时错误日志写入完整 query；代理可用性通过 HTTP 状态／健康探测监控。应用 JSON 日志不包含原始输入，但甲方负载均衡、WAF、云平台等额外设施需单独核对脱敏与访问限制，不能据本模板承诺所有外部设施已配置。

支付补偿使用持久任务和数据库领取，与应用进程分离。安装 `backend/deploy/chinese-study-payments.service`／`.timer`：每次服务退出一分钟后执行 `python manage.py run_payment_tasks --limit 50`，oneshot 最长 600 秒，同一服务运行期间不会重入。安装 `chinese-study-reconciliation.service`／`.timer`：每小时执行 `python manage.py schedule_payment_reconciliation --limit 1000 --older-than-hours 24`，为超过 24 小时的订单安排核查；平台查单确认结果后才改变权益。模板路径、账号及环境文件按本机实际情况调整，在正式渠道配置可用后执行 `systemctl enable --now chinese-study-payments.timer chinese-study-reconciliation.timer`，并检查 journal 与任务积压。此处提供模板，不表示已在服务器启用。

失败任务达到重试上限后保留现场，不通过定时器自动重置。支付核查人员先在后台查看任务／订单／平台结果，再使用带理由和确认预览的重新调度操作；重新调度不会直接改订单或发权益。客户端请求和内存任务均不能替代平台消息、查单和持久补偿。Django `clearsessions` 只清理后台 Session，自建 `StudentSession` 按 expires_at/revoked_at 判定无效，保留记录且不通过该命令删除；不得删除订单、已兑换码、来源或审计历史。

正式交付还需甲方完成主体限制、备案、类目、虚拟支付和 Apple 配置，提供 DNS/TLS、服务器、备份存储与前端 Android／iOS 联调环境。
