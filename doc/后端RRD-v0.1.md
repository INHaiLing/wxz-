## 1. 目标、范围与当前事实

### 1.1 本次目标

为现有原生微信小程序设计服务端和 Web 管理后台，使运营人员能够更新题库，学员能够获取所购权益、兑换激活码，并保留个人学习记录。当前先完成不依赖商业规则的题库后台与受保护查询接口；收到集中答复后，再冻结并实施商品、学习同步和交易规则。

完整业务版本的后续实施范围建议包括（不等同于本轮最小交付）：

- 原生小程序接入微信登录、题库接口、学习同步、商品/权益展示、合规支付入口、订单查询和激活码兑换。
- Web 后台管理分类、篇目、题目、导入、发布、商品、订单、权益、激活码、用户及操作日志。
- 服务端统一处理内容权限、支付状态、权益发放、退款结果和激活码兑换；运营可追溯每次关键变更。

暂不加入自动判卷、错题本、排行榜、社交、AI 出题、直播课、多租户、微服务或学员 Web 学习端。Web 是否允许学员购买由 Q05 决定，不能默认为已有需求。图片、音频、解析和公式由 Q13 确认后纳入。

### 1.2 已实现的前端基线

| 项目 | 当前事实 | 后端接入要求 |
| --- | --- | --- |

## 2. 技术选型与复用边界

### 2.1 推荐方案

采用 **Python 3.13 + Django 5.2 LTS + Django REST Framework（DRF）+ Django Unfold + django-import-export + PostgreSQL**。采用模块化单体，同一业务服务提供小程序 API 和 Web 管理后台。

选择依据是本项目第一版以题库维护、表格导入、后台权限、订单与权益记录为主。Django Admin 已提供成熟的模型管理、表单、登录与权限基础；Unfold 提供后台界面；django-import-export 提供表格导入导出基础；DRF 承担小程序接口。与为这些功能逐项搭建 Node.js 后台相比，这一组合更贴合当前交付内容。现有原生小程序 JavaScript 可以通过 HTTP 接入 Python，无需重写客户端。

这不是因为 Node.js 无法胜任，也不预设 Python 在本项目存在性能优势。开发开始时锁定各库的兼容补丁版本和 PostgreSQL 受支持版本，保存依赖锁定及许可证清单；不得只写宽泛版本后直接部署。

### 2.2 复用与自研划分

| 能力 | 复用基础 | 本项目仍需开发 |
| --- | --- | --- |
| 后台页面、登录、表单 | Django Admin、Unfold | 题库预览、发布流程、订单详情、权益来源、兑换记录及运营提示 |
| HTTP API | DRF | 微信会话、内容授权、学习同步、续学与交易接口 |
| 题库导入导出 | django-import-export | 模板、关联校验、草稿预览、错误行报告、稳定 ID 及整批发布策略 |
| 数据持久化 | PostgreSQL、Django ORM | 唯一约束、事务、迁移、订单与权益的一致性 |
| 虚拟支付 | 微信官方 `xpay` 能力与消息推送 | 适配层、订单映射、回调处理、查单补偿、退款与权益联动 |
| 激活码 | 本项目业务模块 | 批次规则、原子兑换、权限、导出、撤销与审计 |

后台 UI 框架不等于现成商业系统，普通微信支付 SDK 也不等于支持小程序虚拟支付。调研项目可参考其结构或复用适配组件，但不整包接入未经核查的支付、卡密或教育源码。

### 2.3 服务结构与部署原则

- 单体内按身份、内容、学习、商品/权益、交易、激活码、审计划分模块，模块共享数据库，通过明确服务方法完成业务写入。
- Web 后台首期采用 Django Admin + Unfold，自定义必要页面和操作；不另建一套 React/Vue 管理端及重复权限体系。
- 小程序只访问公开 HTTPS API；管理端使用独立权限与会话，发布时配置 HTTPS、合法请求域名、持久数据库、备份和日志。
- 查单、补偿和过期处理先使用可重复运行的管理任务及调度器。是否增加任务队列、缓存服务和对象存储依据实际媒体需求与运行数据决定，不先引入微服务或虚构并发指标。
- 开发、测试、生产的数据库、应用密钥、支付环境和回调地址隔离。服务器、域名、管理员人数、首批用户量与预算由 Q16 确认。

## 3. 角色、后台导航与页面流程

### 3.1 角色建议

| 角色 | 可进行的业务 | 默认不能进行的业务 |
| --- | --- | --- |
| 未登录访客 | 查看允许公开的目录和试学内容 | 查看个人记录、订单、兑换激活码 |
| 已登录学员 | 学习已授权内容、保存记录、查询自己的订单、兑换激活码 | 查看其他用户数据、决定支付成功状态 |
| 题库编辑 | 编辑题目、导入草稿、预览 | 修改价格、退款、导出激活码、直接发放权益 |
| 题库审核/发布人员 | 检查草稿、发布与下架 | 默认不具有财务或激活码导出权限 |
| 运营/客服 | 按授权查询用户、订单、权益与兑换记录 | 修改已确认交易金额、绕过审计删除记录 |
| 财务/交易管理员 | 核查订单与退款、查看必要交易记录 | 默认不编辑题库或导出有效激活码 |
| 超级管理员 | 管理角色和必要配置，处理经审计的特殊操作 | 不提供清空审计或伪造支付成功的普通入口 |

小团队可以由一个人兼任多个角色，但服务端权限仍分开；人员数量及具体分工待 Q16。是否强制两人审核待 Q14，不能假定当前团队有专职审核员。

### 3.2 后台页面

| 页面 | 展示与主要操作 | 状态与交互结果 |
| --- | --- | --- |
| 工作台 | 待发布数量、失败导入、待核查订单、退款待办 | 点击进入对应列表；不展示未经定义的收入统计口径 |
| 分类与篇目 | 来源、名称、排序、地区/年份（如启用）、状态、题量 | 编辑保存草稿；被题目引用的项禁止直接物理删除 |
| 题目列表/编辑 | 稳定 ID、归属、题型、题干、答案、标签、版本、发布状态 | 支持检索筛选、预览默写/背诵；离开未保存表单前提醒 |
| 题库导入 | 下载模板、上传文件、字段匹配、预检结果、错误行 | 全部通过后确认导入草稿；失败保留原文件与报告，未确认前不发布 |
| 发布管理 | 待发布新增/修改/下架清单、校验结果、发布说明 | 一次发布产生一个版本，成功后学员获取新版本；失败不暴露半批内容 |
| 用户与学习概况 | 账户状态、权益、收藏/掌握数量、最近同步时间 | 按权限查询；不默认允许客服改学员掌握状态 |
| 商品与权益 | 商品范围、价格、期限、状态；用户权益来源与生效区间 | 改价仅影响新订单；权益详情可追溯订单或激活码 |
| 订单与支付详情 | 商户订单标识、用户、商品快照、金额、状态、支付/退款事件 | 查询平台状态、查看补偿结果、登记退款；不能手填“已支付”替代核查 |
| 激活码批次/明细 | 商品、数量、发放方式、有效期、使用状态、兑换账户、机构标记（如启用） | 生成、按权限导出、禁用未用码、查看使用历史；重复导出规则待 Q09 |
| 退款与异常处理 | 申请原因、负责人、平台结果、权益变化、处理记录 | 根据渠道能力发起或跟踪退款；失败可重试，不能把备注视作成功结果 |
| 管理员与审计 | 角色、操作人、对象、时间、结果、变更摘要 | 筛选追溯；敏感导出和批量操作须记录用途或备注 |
| 基础配置 | 正式考试日期、默认学习目标、客服说明、渠道开关 | 保存校验后生效；敏感密钥由部署配置管理，不在普通后台明文展示 |

所有列表需要加载、空、失败和无权限状态。删除、批量禁用、发布、退款等操作展示对象与影响范围，确认后执行；网络重试不重复提交业务。表格是否包含机构字段、地区年份等取决于问卷答复。

## 4. 题库编辑、导入、发布与内容提供

### 4.1 内容结构

沿用现有 `source`（`literature/classical`）、`type`（`fact/word/translation`）、分类/篇目关系、`stem` 与 `answers` 展示约定，增加稳定业务 ID、排序、草稿版本和发布状态。题目 ID 不因修改题干、调整排序或重新导入而改变；新增题使用新 ID。

文学分类与收藏分类应使用明确的来源/类型字段关联，不再依赖 `classical-` 字符串前缀或固定 8 个分类来推断。后台可以维护排序；客户端按服务端返回的分类元信息展示。

文言篇目弹窗目前仅有重点字词和重点翻译。`fact` 文言常识按既有随机与收藏路径展示，后台提示其不会出现在篇目弹窗练习中；若要增加入口，需另行确认前端交互，不能自行改动已确认规则。

### 4.2 首期导入格式与步骤

建议首期采用 XLSX 模板加后台单题编辑。模板使用人能填写的列：题目 ID、来源、分类标识、篇目标识、题型、标签、排序、题干、答案 1…答案 N；实际列与正式题库样例核对后冻结。地区/年份、媒体和解析是否加入由 Q12–Q13 决定。

导入流程：下载模板 → 上传 → 预检 → 展示新增/更新/错误行 → 用户确认 → 写入草稿 → 预览 → 发布。Word/PDF/图片不默认承诺自动准确转换；收到样例后决定一次性整理或后续导入工具。

必须校验：

- 来源、题型和关联项有效；文学题有有效分类，篇目题有有效篇目。
- 题目 ID 唯一；已存在 ID 明确表示更新，不根据相似题干自动覆盖。
- 题干非空，占位符编号均有对应答案；答案非空，不允许错位或遗失。
- 文件内重复 ID、无效引用、非法字段和超限文件给出行号及原因；大小和行数上限依据正式样例与测试确定。
- 题库素材来源及收费授权由运营确认，不把提供了文件等同于具备收费分发权（Q12）。

默认建议：一批预检全部通过才写入该批草稿；不静默跳过错误行。导入不直接覆盖学员当前可见版本。导出表格按权限提供，并防止将用户输入当作表格公式执行。

### 4.3 发布与修订

内容经过草稿、已发布、已下架状态。发布操作校验整批改动，以事务形成新的可见版本；编辑草稿时学员仍看到旧版本。回退通过发布一个可审计的恢复版本完成，不删除历史版本。

已下架题不再进入新练习，但学习记录仍可追溯。纠正错字或答案是否重置“已掌握”由 Q14 决定；建议默认保留学习历史，重大知识修订由运营明确发起重新学习提示。题库更新不因分母变化伪造新学习行为。

正式上线不发布“待补充篇目”占位项。没有题目的正式篇目可保留明确空态，但不参与“已学篇目”判断；完成率的分母范围在 Q01、Q03、Q14 定稿时说明，并与首页文案一致。

### 4.4 内容访问与随机练习

目录可按试学政策返回元信息，题干与答案的完整访问必须经过服务端授权。不得提供一个未鉴权的全量题库下载入口。已授权内容到达客户端后无法承诺绝对防复制，因此防护目标是控制未授权访问与减少无意泄露。

顺序练习按发布版本和排序分页，每组最多 5 题。随机练习建议由服务端建立一轮会话，固定题库版本、来源及本轮有权访问的题目顺序；每组最多 5 题、一轮不重复。收藏、掌握及模式切换不重置该轮。末组操作生成新一轮，继续学习恢复原轮位置。

题目下架、权益失效或续学记录失效时跳过不可用内容并给出说明；若剩余为空则返回明确空态。当前一轮不会自动插入刚发布的新题，下一轮使用新版本。

## 5. 微信登录、学习同步与旧记录迁移

### 5.1 身份与会话

小程序通过 `wx.login` 获取临时凭证交给后端，后端与微信换取身份并建立内部用户 ID。OpenID 用于关联当前小程序身份，不直接作为前端可指定的授权条件；不把 session_key、AppSecret 或支付密钥下发客户端。

小程序持有服务端颁发的有效会话，后台使用独立的管理员 Session 与权限；会话机制、有效期与刷新策略在接口定稿时统一配置。未登录可见范围依据 Q03；访问个人记录、订单和激活码兑换前必须登录。身份失效时保留当前页面上下文，重新登录后恢复操作，不能创建重复订单。

暂不强制收集手机号、真实姓名或身份证信息。若后续确需这些字段，先说明业务用途和最小范围。Web 学员购买账户如何与微信关联由 Q05 决定，不能用让用户填写任意 OpenID 的方式认领订单。

### 5.2 学习数据与统计

收藏和掌握接口采用“设置为 true/false”的幂等操作，不能直接把客户端 `toggle` 语义当作可重试 HTTP 命令。服务端以账户、题目和操作标识校验，返回确认后的状态与版本。

建议保留以下既有含义：

- 收藏与掌握独立，收藏取消后不影响掌握。
- 学习日按发生掌握操作的日期去重；取消掌握不删除学习日历史。
- 今日数量不因同题重复点击而重复累计；统计口径在需求定稿中明确写给用户。
- 模式可全局记忆；续学保存类型化学习上下文和有效题目 ID，前端将其映射到允许的页面，不执行服务端任意路由字符串。
- 权益到期或退款不自动删除学习历史，只影响是否还能访问受限内容。

所有交易有效期和学习统计的业务日使用统一时区（建议 Asia/Shanghai），后台保存可追溯时间戳。客户端时间不能决定支付状态、激活码期限或权益到期。

跨设备与离线策略由 Q15 确认。建议支持短暂断网时的本地待同步操作，联网后幂等提交；出现冲突时采用服务端版本与明确的合并结果，不把保存失败显示为成功。账号切换必须隔离题库授权缓存与个人记录。

### 5.3 现有记录迁移

现有键名为 `chinese-study.frontend.v1`，包含 `version、favorites、mastered、studyDates、mode、resume`，没有账户归属。当前合法题目集合固定从演示数据生成，接后端前必须替换这段校验，否则线上新题 ID 会被清除。

是否迁移由 Q15 决定。若迁移，采用以下方案：

1. 首次登录发现本机旧记录，展示归入当前账户的提示，由用户确认归属。
2. 服务端根据明确的旧 ID → 正式 ID 映射校验；不依据题干相似度自动认领正式题。
3. 建议收藏与掌握取已确认记录并集、学习日去重；模式和续学采用最新有效记录。最终合并规则随 Q15 固定。
4. 一次迁移有唯一标识，重试不会重复写入；服务器确认成功后客户端才标记完成，并保留旧记录备份。
5. 无法匹配、已下架或没有权限的记录在结果中说明，不悄悄丢弃整份记录；权限不足与记录不存在分开处理。

如果本地记录仅是开发验收数据，建议生产首次上线不迁移演示记录；该建议不能代替用户答复。

## 6. 商品与统一权益

商品描述“购买什么、价格多少、有效多久”；权益描述“某个用户现在能访问哪些内容”。支付和激活码都是权益来源，应进入同一发放与鉴权服务。

商品至少维护售卖范围、价格、期限规则和启用状态。订单创建时保存商品及价格快照，后续改价不追溯旧订单。范围可能是全部题库、模块、地区或年份，最终由 Q01–Q02 确定；第一版不提前实现任意规则引擎。

权益记录保留用户、范围、生效区间、状态与来源。来自不同订单/激活码的权益分别留痕；有效访问范围是所有当前有效来源的合并结果。每个来源最多产生一次对应权益发放。

重复购买、重复兑换、有效期叠加、是否可转移由 Q10 确认。后端下单和兑换前必须按规则处理，不允许静默吞掉用户已付款或已兑换的价值。

退款或撤销时仅处理对应来源的权益，不能清空该用户从其他订单或激活码获得的有效访问权。若采用续期堆叠，需要按保留的来源重新计算时间区间，并在验收中覆盖撤销中间一笔的情形。

## 7. 支付、扫码、订单与退款

### 7.1 官方支付路径与开通前提

本项目售卖的是题库访问等虚拟内容。依据本次调研，小程序支付方案应围绕官方虚拟支付 **`wx.requestVirtualPayment` 的道具直购（xpay）** 设计，不能默认使用普通 JSAPI/Native 收取题库费用。iOS 已有有条件支持能力，实际范围取决于主体、开通配置、渠道规则和客户端条件；不能写成“iOS 一律不能付”或“所有 iOS 均可直接支付”。参见 [微信小程序虚拟支付官方说明](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment.html)。

开通前由 Q06–Q07 确认主体、认证、备案、服务类目、虚拟支付能力和系统覆盖范围。实施时核对官方最新文档及该账号后台实际权限，建立平台与渠道能力开关；未满足条件时展示明确提示，不偷偷切到其他收款方式。

### 7.2 扫码场景

“扫码”是入口方式，未必是一张支付二维码。推荐候选流程是：用户扫描合规的小程序码/入口码 → 打开指定商品 → 微信登录 → 核对商品和账户 → 在小程序内走官方虚拟支付。这样可直接关联权益归属。

Q04 尚未回答，因此这一流程是建议而非最终承诺。若要求电脑网页展示付款码或在另一设备付款，应结合 Q05 核实账户绑定、官方允许的交易场景和渠道能力。普通个人收款码不能替代具有订单关联、支付确认和权益发放的服务端交易流程。

### 7.3 下单与支付流程

1. 已登录用户查看商品和已有权益，服务端按 Q10 规则判断是否可购买。
2. 服务端以商品配置生成订单和金额快照，校验客户端环境与可用支付渠道；客户端提交的金额不能作为收费依据。
3. 支付适配层按官方 xpay 规则准备支付信息；仅向当前订单所属用户返回调用所需字段，不暴露服务端密钥。
4. 小程序调用官方支付能力。用户取消、调用失败或客户端回调成功都不直接改变最终权益。
5. 平台通知与服务端查单共同驱动订单确认；核对应用、渠道、订单、商品/金额及状态等必要信息。
6. 订单确认与权益发放通过事务和唯一约束保证同一来源只发一次；前端查询订单及权益，确认后进入学习。
7. 未完成订单显示可恢复状态；重开小程序仍能查询自己的订单，不能因用户关页漏发权益。

内部金额建议按最小货币单位存储，支付适配时严格按该平台字段单位映射。xpay 的签名、商品标识和请求结构以官方协议为准，不能从普通微信支付 V3 参数照搬。

### 7.4 回调、查单与补偿

虚拟支付回调接入小程序消息推送，采用官方消息推送安全模式的校验、解密和响应要求；**不是普通微信支付 V3 的通知验签流程**。具体事件、重试与返回格式以 [微信消息推送官方说明](https://developers.weixin.qq.com/miniprogram/dev/framework/server-ability/message-push.html) 及虚拟支付文档为准，支付适配层负责隔离这些差异。

- 先校验消息来源与内容，再落库处理；保留必要事件标识和处理结果，敏感内容脱敏。
- 通知可能重复或乱序，查单也可能与通知同时发生；两条路径必须调用同一幂等“确认订单并发放权益”服务。
- 本地待支付不代表平台未扣款；超时、关单与迟到通知应查平台实际状态后处理。
- 已付款未发放、状态长期不明或消息处理失败进入待核查队列，可自动重试并供后台查看；重试仍不得重复发放。
- 不允许后台通过直接修改数据库状态伪造支付成功；运营修复须有核查依据和审计记录。

### 7.5 退款与撤销

退款标准、负责人、处理时限及权益收回时间由 Q11 确定。后台需保存申请、审批/处理、平台执行结果与权益变化，区分申请中、处理中、成功和失败；前端申请成功不等于实际退款成功。

普通虚拟支付可依据平台能力由开发者发起退款；Apple 支付由用户向 App Store 申请，开发者不能主动发起退款，后端需处理退款问询与退款完成推送。后台应按支付渠道显示对应的处理操作，不向全部订单提供同一种“发起退款”按钮。实际账户权限、接口条件与期限在接入时继续按[官方虚拟支付文档](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment.html)核验。人工处理也需要外部结果依据，不能把财务备注当作平台退款结果。

退款成功后按确认政策撤销或调整对应订单来源权益，并重新计算剩余有效来源。保存订单、退款、学习记录和审计历史。已退款订单的迟到支付通知不能再次激活权益；特殊争议状态需核查后处理。

## 8. 激活码生成、发放、兑换与管理

### 8.1 商业来源先确认

Q08 区分免费赠送、机构采购、外部售卖及发放者；Q09 确认单码次数、截止日期、机构标记与重复导出。激活码不是规避平台支付规则的默认通道，不能保证任何外部售码或导流方式合规。来源、发放和兑换入口须核对当前平台规则后启用。

### 8.2 批次生成与保管

创建批次时选择已配置商品/权益、数量、可兑换期限及业务备注；是否支持多人多次、机构归属待 Q09。建议第一版优先单码单人一次，避免共享码造成归属争议，但未答复前不强制当作商业规则。

使用密码学安全随机码，避免可预测流水号。服务端默认存校验摘要；展示和导出权限单独控制，审计记录不包含完整有效码。若 Q09 要求重复导出原码，需要额外采用加密保管与受控解密导出；不能一边只存不可逆摘要，一边承诺随时重新导出原码。

批次、单码启用/禁用、导出和作废均记录操作人、对象、时间和理由。禁用未用码与撤销已经发放的权益是两个不同操作，界面必须说明影响。

### 8.3 兑换流程

已登录用户输入码 → 服务端规范化输入并限频 → 校验批次、码状态、有效期、剩余次数、商品状态和重复权益规则 → 在数据库事务中占用次数并发放同一来源权益 → 返回兑换结果与当前权益。

请求需要幂等标识；并发使用同一码时按既定次数规则只成功允许的次数。同一用户因超时重试应看到已完成的兑换结果，不能重复扣次数或发放。无效、到期、已使用、禁用与暂时失败需有可理解提示，同时避免提供可被批量枚举的敏感信息。

Q10 决定已有权益如何处理，Q11 决定误发码、撤销和恢复规则。撤销兑换仅影响该兑换来源，其他来源权益保持按规则有效。

## 9. 最小数据实体与一致性约束

以下是拟新增业务模型，并非仓库已经存在的字段或数据库表。详细字段在答复商业规则后确定。

| 实体 | 最少需要表达的信息 | 关键约束 |
| --- | --- | --- |
| 用户/微信身份 | 内部用户 ID、应用内微信身份关联、账户状态 | 同一应用身份唯一，不由客户端任意指定归属 |
| 分类/篇目 | 稳定 ID、来源、名称、排序、状态 | 被引用项不可直接物理删除；占位内容不正式发布 |
| 题目/修订 | 稳定 ID、关联、题型、题干、答案、标签、排序、版本 | 占位符合法；内容修改与 ID 分离 |
| 题库发布/导入任务 | 版本、改动摘要、结果、操作人、时间、错误行 | 发布原子生效，导入与发布分开 |
| 用户题目状态 | 用户、题目、收藏、掌握、时间/版本 | 用户与题目组合唯一，设置状态可幂等重试 |
| 学习日/偏好/续学 | 学习日期、模式、学习上下文、有效题序及位置 | 学习日去重；账号隔离；上下文能验证有效性 |
| 随机练习轮次 | 用户、来源、发布版本、固定题序、当前位置 | 一轮不重复，服务端控制可访问题 |
| 商品 | 售卖范围、价格、期限、状态、支付渠道映射 | 未启用或能力不足时禁止新下单 |
| 订单 | 用户、商品/价格快照、商户订单标识、状态 | 标识唯一，金额不可被客户端修改 |
| 支付/退款事件 | 渠道标识、外部记录、金额、状态、核查及处理结果 | 重复事件幂等，平台状态与内部状态可追溯 |
| 权益来源 | 用户、范围、起止时间、来源类型/ID、状态 | 同一来源唯一发放；撤销仅影响该来源 |
| 激活码批次/码 | 商品、期限、次数规则、状态、摘要/受控密文 | 码唯一、次数原子更新、原码导出受控 |
| 兑换记录 | 用户、码、请求标识、结果、关联权益 | 防并发超兑；请求重试返回同一结果 |
| 管理员/权限/审计 | 角色、操作人、对象、变更摘要、时间、结果 | 敏感操作必须服务端授权及留痕 |

内容状态、订单状态、退款状态和权益状态分开建模，不能用一个“已付款”布尔值承载全部流程。必要唯一约束应在数据库层落实，不能仅依赖“先查询再新增”的应用逻辑。

## 10. 建议 API 边界与前端接入

以下路径是拟定的第一版接口边界，方便后续 OpenAPI 设计；不是已上线接口。服务端返回统一可识别的错误码、简明提示及请求追踪标识，分页和版本字段在接口定稿中保持一致。

| 接口边界 | 建议方法/路径 | 主要用途与权限 |
| --- | --- | --- |
| 微信会话 | `POST /api/v1/auth/wechat/session` | 临时登录凭证换本站会话；不返回微信服务端密钥 |
| 当前账户/权益 | `GET /api/v1/me`、`GET /api/v1/me/entitlements` | 返回本人资料与有效权益摘要 |
| 公共配置 | `GET /api/v1/config` | 正式考试日期、公开配置、客户端可用能力 |
| 分类/篇目 | `GET /api/v1/categories`、`GET /api/v1/articles` | 已发布元信息、顺序及允许公开的题量 |
| 题目列表/详情 | `GET /api/v1/questions`、`GET /api/v1/questions/{id}` | 按来源、分类、篇目、题型取授权内容；有分页与版本 |
| 题目个人状态 | `PUT /api/v1/me/questions/{id}/state` | 显式设置收藏/掌握，校验归属与幂等 |
| 个人收藏/统计 | `GET /api/v1/me/favorites`、`GET /api/v1/me/study-summary` | 本人的分类收藏与统一口径统计 |
| 续学 | `GET/PUT /api/v1/me/resume` | 读取或保存经验证的学习上下文 |
| 本地记录迁移 | `POST /api/v1/me/study-imports` | 仅在 Q15 同意后启用，校验旧 ID 映射与迁移幂等 |
| 随机轮次 | `POST /api/v1/practice-rounds`、`GET /api/v1/practice-rounds/{id}/groups/{index}` | 建立并读取固定题序，校验当前用户与权益 |
| 商品 | `GET /api/v1/products` | 只返回当前用户环境可购买的商品与规则 |
| 订单 | `POST /api/v1/orders`、`GET /api/v1/me/orders`、`GET /api/v1/me/orders/{id}` | 创建订单及查询本人订单；重复请求不重复创建 |
| 支付调用准备 | `POST /api/v1/me/orders/{id}/payment-attempts` | 服务端核验后返回官方支付调用所需信息 |
| 激活码兑换 | `POST /api/v1/me/activation-redemptions` | 登录、限频、原子兑换与统一发放权益 |
| 退款申请 | `POST /api/v1/me/orders/{id}/refund-requests` | 是否开放给学员及规则待 Q11；不等于直接退款 |
| 平台消息 | 独立官方消息推送入口 | 由微信消息安全模式验证，不沿用管理员或学员会话 |

后台先使用 Django Admin 自身页面和受权限控制的动作，不为每个表额外开发通用 CRUD API。需要自定义页面时调用同一业务服务，避免后台绕过发布校验、兑换限制或订单幂等规则。

原生页面接入时须将同步数据调用改为异步服务，统一处理加载、超时、未登录、权益不足、无内容和重试。保留原有题卡字段和组件交互，在适配层合成 `favorite/mastered`，不把支付判断散落到每个组件中。

新增登录引导、商品/权益、订单、兑换和结果页面的具体路由在支付场景确认后固定；保留原有 6 个学习路由。所有直达入口、收藏、随机、续学和单题请求都接受服务端授权，不能只拦截首页入口。

## 11. 权限、安全与运行保障

- 管理端权限在服务端校验，题库编辑、发布、退款、发放/撤销权益和原码导出分别授权。高影响操作显示具体对象及影响范围并记录审计。
- 小程序请求根据本站会话关联用户，所有订单、练习轮次、学习记录和兑换详情检查对象归属，防止通过改 ID 访问他人数据。
- API 与管理端使用 HTTPS；后台 Session 操作启用 CSRF 防护。敏感配置来自部署环境或受控密钥配置，不写入前端、仓库或普通日志。
- 激活码兑换、登录和下单设置可配置限频；文件上传验证类型和体积；题库富文本/媒体如启用需单独处理安全展示。
- 正式受限题目不打包到小程序公开静态资源；账号退出清理敏感缓存。允许离线缓存的范围与时长须结合 Q15 和权益政策定义。
- 支付通知、查单和退款都记录必要证据与处理结果，日志脱敏。审计需要可保留和检索，不设置普通业务人员清空按钮。
- 数据库备份与恢复作为上线检查项；日志、导入文件、导出文件和历史记录的保留期限在运营配置中明确，不无限期堆积。
- 监测接口错误、异常登录/兑换、支付已确认但权益未发放、持续待核查订单、任务失败及备份失败。具体阈值依据运行情况设定，不编造当前负载。

## 12. 阶段实施与交付

| 阶段 | 工作内容 | 交付与进入下一阶段的条件 |
| --- | --- | --- |
| 0 需求与能力核实 | 用户集中回答 Q01–Q17；核查虚拟支付资质、系统范围、扫码场景、正式题库样例 | RRD 定稿、商品/激活/退款规则、官方能力核实记录；未明确商业规则不直接上线收款 |
| 1 服务端与后台基础 | Django 单体、数据库、环境配置、管理员权限、审计、API 基础及会话 | 可登录后台和测试身份接口，部署与密钥配置文档 |
| 2 题库运营闭环 | 分类/篇目/题目、XLSX 导入、预览、发布、下架、版本与授权内容接口 | 运营完成一批题库从文件到小程序可见的演练，失败批次不影响现网内容 |
| 3 学习同步与统一权益 | 收藏/掌握/统计/续学、随机轮次、商品及权益、可选旧记录迁移 | 保持原学习行为，跨设备及越权测试通过；演示数据与正式数据边界清楚 |
| 4 激活码管理 | 批次生成、导出策略、禁用、原子兑换、权益关联及审计 | 并发兑换、重复请求、失效码、误发撤销和剩余权益验收通过 |
| 5 官方虚拟支付 | xpay 适配、入口/二维码场景、订单、消息安全模式、查单、补偿及退款联动 | 在实际开通环境和支持系统验证支付闭环；不以普通支付或静态成功页替代 |
| 6 联调与发布准备 | 原生页面接入、状态反馈、角色验收、备份恢复、操作手册、环境核对 | 完整验收记录、待处理限制、可回退发布方案；真实收款发布由确认的运营条件决定 |

题库、学习同步和后台基础可先并行实施；支付模块须建立在已确定的商品/权益规则和官方能力之上。可以分工开发，但共享订单确认与权益发放服务由统一负责人维护，避免出现支付版和激活码版两套解锁逻辑。

## 13. 验收清单

| 场景 | 应观察到的结果 |
| --- | --- |
| 文学、字词、翻译与模式切换 | 保留现有内容渲染规则，默写隐藏答案，背诵展示答案，切换不改变题序 |
| 收藏与掌握 | 独立设置；重复请求不翻转或重复统计；跨页/跨设备结果一致 |
| 随机与续学 | 每组最多 5 题，一轮不重复，末组可新开；重新进入可恢复有效位置 |
| 多设备/账号切换 | 不串账户记录或题目授权；网络失败给出待同步/重试反馈 |
| 题库新增与修订 | 稳定 ID 保持，草稿不可见，发布整批生效，下架不删除学习历史 |
| 错误导入 | 显示行号和原因；不半批发布，不覆盖已有有效数据 |
| 受限内容访问 | 修改路由、题目 ID、收藏或随机入口都不能越过服务端权益校验 |
| 试学与购买 | 免费范围与商品说明一致；价格来自服务端，未启用渠道无法下单 |
| 取消支付/退出页面 | 不误发权益；已付款的订单能通过查询和补偿完成发放 |
| 重复/乱序通知与查单并发 | 同一订单只发一次权益，已退款来源不被迟到通知重新激活 |
| 金额/应用/归属不符 | 拒绝错误确认，留下核查记录，不泄露其他用户订单 |
| 多来源与退款 | 仅撤销该退款来源，其他订单或激活码权益继续按规则有效 |
| 激活码并发与重试 | 不超兑；同一成功请求重试返回既有结果，失败不扣次数 |
| 无效/禁用/过期码 | 不发权益，提示明确；错误尝试被限频且不暴露完整有效码 |
| 后台权限 | 题库编辑不能退款/导码；隐藏按钮和直接请求都受限制 |
| 备份恢复与补偿任务 | 能恢复关键数据；重复运行任务不重复收款、发放或退款 |

支付验收需覆盖计划支持的 Android/iOS 及实际版本条件；测试方式和环境按官方能力安排。正式收款验收记录需区分模拟、测试环境与真实交易，不能把接口桩成功当成渠道开通成功。
