## 1. 目标、范围与当前事实

### 1.1 本次目标

为甲方安排开发的微信小程序提供后端服务、现有 Django Web 管理后台及接口契约，使运营人员能够维护题库、商品和激活码，服务端能够验证学员身份、试学及付费访问、兑换权益和学习记录。最小题库后台与受保护查询接口已经完成；后续按已明确的业务规则分阶段增加服务端能力。

完整业务版本的后续实施范围如下，不等同于已完成的最小交付：

我方后端可通过接口请求与自动化用例独立验收，不以学员页面完成为前提；真实支付上线仍须在已开通渠道上完成联合验证。前端工作不纳入我方代码交付和工时承诺，接口联调支持不等于代为开发前端。

### 1.3 待答规则的处理原则

已确认的价格、范围、永久权益、禁止重复开通、发码及撤销规则直接进入规格，不再重复询问。永久权益不再依赖期限起算或续期堆叠算法；退款异常细节、学习规则或规模预算不能由技术假设冒充业务答复。按阶段实现已有依据的模块，不为延期支付建立空业务流程；正式支付须依据平台能力开通，没有资质或渠道未启用时，服务端必须禁止该渠道下单。

## 2. 技术选型与复用边界

### 2.1 推荐方案

采用 **Python 3.13 + Django 5.2 LTS + Django REST Framework（DRF）+ Django Unfold + django-import-export + PostgreSQL**。采用模块化单体，同一业务服务提供小程序 API 和 Web 管理后台。

选择依据是本项目第一版以题库维护、表格导入、后台权限、订单与权益记录为主。Django Admin 已提供成熟的模型管理、表单、登录与权限基础；Unfold 提供后台界面；django-import-export 提供表格导入导出基础；DRF 承担小程序接口。与为这些功能逐项搭建 Node.js 后台相比，这一组合更贴合当前交付内容。甲方前端通过 HTTP 契约接入，不受服务端使用 Python 的限制。

这不是因为 Node.js 无法胜任，也不预设 Python 在本项目存在性能优势。开发开始时锁定各库的兼容补丁版本和 PostgreSQL 受支持版本，保存依赖锁定及许可证清单；不得只写宽泛版本后直接部署。

### 2.2 复用与自研划分

| 能力 | 复用基础 | 本项目仍需开发 |
| --- | --- | --- |
| 后台页面、登录、表单 | Django Admin、Unfold | 题库预览、发布流程、订单详情、权益来源、兑换记录及运营提示 |
| HTTP API | DRF | 微信会话、内容授权、学习同步、续学与交易接口 |
| 题库导入导出 | django-import-export | 模板、关联校验、草稿预览、错误行报告、稳定 ID 及整批发布策略 |
| 数据持久化 | PostgreSQL、Django ORM | 唯一约束、事务、迁移、订单与权益的一致性 |
| 虚拟支付 | 微信官方 `xpay` 能力与消息推送 | 适配层、订单映射、回调处理、查单补偿、退款与权益联动 |
| 激活码 | 本项目业务模块 | 批次规则、原子兑换、权限、导出、撤销与审计 |

后台 UI 框架不等于现成商业系统，普通微信支付 SDK 也不等于支持小程序虚拟支付。调研项目可参考其结构或复用适配组件，但不整包接入未经核查的支付、卡密或教育源码。

### 2.3 服务结构与部署原则

- 单体内按身份、内容、学习、商品/权益、交易、激活码、审计划分模块，模块共享数据库，通过明确服务方法完成业务写入。
- Web 后台首期采用 Django Admin + Unfold，自定义必要页面和操作；不另建一套 React/Vue 管理端及重复权限体系。
- 学员客户端通过 HTTPS 访问按契约授权的 API；管理端使用独立权限与会话，不能将网络可访问理解为无需鉴权。部署时配置 HTTPS、持久数据库、备份和日志；甲方在小程序平台配置相应合法请求域名。
- 查单、补偿和订单超时处理先使用可重复运行的管理任务及调度器；永久权益不设置自动到期任务。是否增加任务队列、缓存服务和对象存储依据实际媒体需求与运行数据决定，不先引入微服务或虚构并发指标。
- 开发、测试、生产的数据库、应用密钥、支付环境和回调地址隔离。服务器、域名、管理员人数、首批用户量与预算由 Q16 确认。

## 3. 角色、后台导航与页面流程

### 3.1 角色建议

| 角色 | 可进行的业务 | 默认不能进行的业务 |
| --- | --- | --- |
| 未登录访客 | 查看允许公开的目录和试学内容 | 查看个人记录、订单、兑换激活码 |
| 已登录学员 | 学习已授权内容、保存记录、查询自己的订单、兑换激活码 | 查看其他用户数据、决定支付成功状态 |
| 题库编辑 | 编辑题目、导入草稿、预览 | 修改价格、退款、导出激活码、直接发放权益 |
| 题库审核/发布人员 | 检查草稿、发布与下架 | 默认不具有财务或激活码导出权限 |

## 4. 题库编辑、导入、发布与内容提供

### 4.1 内容结构

沿用现有 `source`（`literature/classical`）、`type`（`fact/word/translation`）、分类/篇目关系、`stem` 与 `answers` 展示约定，增加稳定业务 ID、排序、草稿版本和发布状态。题目 ID 不因修改题干、调整排序或重新导入而改变；新增题使用新 ID。

文学分类与收藏分类应使用明确的来源/类型字段关联，不再依赖 `classical-` 字符串前缀或固定 8 个分类来推断。后台可以维护排序；客户端按服务端返回的分类元信息展示。

历史文言篇目弹窗仅有重点字词和重点翻译，`fact` 文言常识曾通过随机与收藏路径展示。后端继续支持这些来源和题型，并在接口契约中列清归属及筛选方式；甲方前端自行设计入口，不能把旧弹窗结构当作新的后端访问权限。

### 4.2 首期导入格式与步骤

首期格式已确定为 **XLSX 模板加后台单题编辑**，由我方提供模板及字段说明，甲方按模板整理并交付题库，不再让甲方选择导入格式。沿用现有后台的精确中文表头：`题目ID`、`来源`、`分类ID`、`篇目ID`、`题型`、`标签`、`排序`、`题干`、`答案1`…`答案N`。当前模板默认提供 `答案1` 至 `答案7`，需要时可连续扩展至 `答案32`；不得在答案列编号中插入空格或断号。模板同时提供填写说明、例题及现有分类/篇目 ID 参考。

甲方须保留稳定 `题目ID`，按参考 ID 填写归属；`{{0}}` 对应 `答案1`，后续按顺序对应。`来源` 使用 `literature/classical`，`题型` 使用 `fact/word/translation`。正式题量、具体内容、来源及收费使用授权仍属 Q12 的交接事项；地区/年份、媒体、解析、公式和新题型是否加入由 Q13 确认，不预先增加模板字段。

导入流程：后台下载模板 → 甲方按模板整理 → 上传 → 预检 → 展示新增/更新/错误行 → 管理员确认 → 写入草稿 → 预览 → 发布。Word/PDF/图片如是原始素材，由甲方先整理进模板；自动识别、转换和代录题库不纳入本次交付。

必须校验：

- 来源、题型和关联项有效；文学题有有效分类，篇目题有有效篇目。
- 题目 ID 唯一；已存在 ID 明确表示更新，不根据相似题干自动覆盖。
- 题干非空，占位符编号均有对应答案；答案非空，不允许错位或遗失。
- 文件内重复 ID、无效引用、非法字段和超限文件给出行号及原因；大小和行数上限依据正式样例与测试确定。
- 题库素材来源及收费授权由运营确认，不把提供了文件等同于具备收费分发权（Q12）。

沿用已实现的规则：一批预检全部通过才写入该批草稿，不静默跳过错误行；确认时检查预检后的内容冲突。导入不直接覆盖当前发布修订。导出表格按权限提供，并防止将用户输入当作表格公式执行。

### 4.3 发布与修订

内容经过草稿、已发布、已下架状态。沿用现有题目级修订：发布校验整批改动，在同一事务中创建所需修订并切换可见指针；编辑草稿时内容接口仍读取旧发布修订。历史修订不删除或原地改写；如后续增加恢复操作，应先恢复为草稿再发布，本次不承诺新增全库版本或回滚界面。

已下架题不再进入新练习，但学习记录仍可追溯。纠正错字或答案是否重置“已掌握”由 Q14 决定；建议默认保留学习历史，重大知识修订由运营明确发起重新学习提示。题库更新不因分母变化伪造新学习行为。

正式上线不发布“待补充篇目”占位项。没有题目的正式篇目可返回明确空结果，但不参与“已学篇目”判断；完成率的分母范围在学习统计接口中说明，并交甲方前端据此展示。

### 4.4 内容访问与随机练习

目录可按试学政策返回元信息，题干与答案的完整访问必须经过服务端授权。不得提供一个未鉴权的全量题库下载入口。已授权内容到达客户端后无法承诺绝对防复制，因此防护目标是控制未授权访问与减少无意泄露。

Q03 已确认：文学以文学分类为免费范围，文言以篇目为免费范围，例如《劝学》免费一页。同一篇目的 `fact`、`word`、`translation` 按已发布题目的固定排序合并确定一个免费题目集合，切换常识、字词或翻译不额外赠送一页；不能对筛选后的每种题型重新取第一页作为免费内容。

每页题数由后台配置，服务端据此确定各分类／篇目的免费集合。这里的“第一页”是学习列表第一页，不按屏幕显示数量计算；后台管理 API 默认 20 条和历史演示每组 5 题都不作为试学规则。普通列表、随机、收藏、续学和详情共用该集合与永久权益检查；修改 `page`、`page_size`、排序或筛选、重复请求和模式切换均不能扩大免费范围。分页配置、免费集合及配置变更的生效方式由后端统一维护并输出契约，客户端不能指定授权容量。

未开通用户可访问免费集合，继续访问集合外内容须购买或兑换永久权益；已有有效永久权益直接读取受限内容。后端对无权请求返回明确授权结果或权益不足状态，不返回完整受限题干与答案；甲方前端据此展示开通提示、商品及支付入口。试学结束是业务提示时机，不是必须完成的购买前置任务，也不以隐藏按钮代替服务端鉴权。

顺序练习按已发布修订、固定排序及正式学习分页配置分组；历史演示每组最多 5 题不约束新前端。随机练习建议由服务端建立一轮会话，保存本轮题目 ID/修订快照、来源及有权访问的题目顺序；按配置分组、一轮不重复，不以此要求新增全库发布版本。收藏、掌握及模式切换不重置该轮；服务端提供新一轮及恢复位置接口，甲方前端负责对应交互。

题目下架、权益失效或续学记录失效时跳过不可用内容，并通过响应状态及原因说明；若剩余为空则返回明确空结果。当前一轮不会自动插入刚发布的新题，下一轮读取最新可用修订。

## 5. 微信登录、学习同步与旧记录迁移

### 5.1 身份与会话

甲方前端通过 `wx.login` 获取临时凭证并调用登录接口；我方后端与微信换取身份、建立内部用户 ID 并颁发本站会话。OpenID 用于关联当前小程序身份，不直接作为前端可指定的授权条件；不把 session_key、AppSecret 或支付密钥下发客户端。真实微信登录验证需要甲方提供对应小程序的受控配置，不把测试身份当作真实登录交付。

学员 API 与后台管理员 Session 使用明确分离的权限边界；会话机制、有效期与刷新策略在接口定稿时统一配置。未登录可见范围依据 Q03；访问个人记录、订单和激活码兑换前必须登录。后端返回统一的会话失效错误和可重试约定，保证交易请求幂等；保留页面上下文和重新登录后的界面恢复由甲方前端实现。

暂不强制收集手机号、真实姓名或身份证信息。若后续确需这些字段，先说明业务用途和最小范围。已明确 Web 仅作管理后台，不规划学员 Web 购买账户；服务端不能允许填写任意 OpenID 认领权益或订单。

### 5.2 学习数据与统计

收藏和掌握接口采用“设置为 true/false”的幂等操作，不能直接把客户端 `toggle` 语义当作可重试 HTTP 命令。服务端以账户、题目和操作标识校验，返回确认后的状态与版本。

建议保留以下既有含义：

- 收藏与掌握独立，收藏取消后不影响掌握。
- 学习日按发生掌握操作的日期去重；取消掌握不删除学习日历史。
- 今日数量不因同题重复点击而重复累计；统计口径在需求定稿中明确写给用户。
- 模式可全局记忆；续学保存类型化学习上下文和有效题目 ID，前端将其映射到允许的页面，不执行服务端任意路由字符串。
- 权益来源退款或撤销不自动删除学习历史，只影响是否还能访问受限内容；永久权益不因时间经过自然到期。

订单超时、交易事件时间和学习统计的业务日使用统一时区（建议 Asia/Shanghai），后台保存可追溯时间戳。客户端时间不能决定支付状态或权益状态；激活码无兑换截止日期，永久权益无自然到期日。

学习同步后端及接口属于我方范围，具体跨设备和冲突合并策略由 Q15 确认。后端负责账户隔离、幂等提交、版本校验及明确的同步结果；甲方前端负责本地待同步队列、断网提示、重试和账号切换后的缓存隔离，不把接口失败显示为保存成功。

### 5.3 现有记录迁移

历史本地键名为 `chinese-study.frontend.v1`，包含 `version、favorites、mastered、studyDates、mode、resume`，没有账户归属；旧校验使用固定演示题目集合。这些只作为迁移来源参考，不代表我方会改造该前端。甲方若继续使用相关代码，其前端人员须移除会误删正式题目 ID 的旧校验。

是否迁移由 Q15 决定。若迁移，采用以下方案：

1. 甲方前端读取本机旧记录，展示归入当前账户的提示，由用户确认归属并提交迁移请求。

4. 后端以唯一迁移标识保证重试不会重复写入；服务器确认成功后，由甲方前端标记完成并保留旧记录备份。
5. 无法匹配、已下架或没有权限的记录在结果中说明，不悄悄丢弃整份记录；权限不足与记录不存在分开处理。

## 6. 商品与统一权益

商品描述“购买什么、价格多少、是否永久有效”；权益描述“某个用户现在能访问哪些内容”。支付和激活码都是权益来源，应进入同一发放与鉴权服务。

商品至少维护售卖范围、价格、永久有效标识和启用状态。Q01–Q02 已确定首期为全部语文题库、初始价格 10 元、支付成功或激活码兑换成功后永久激活，管理员可修改售价。订单创建时保存商品、永久权益规则及价格快照，后续改价不追溯旧订单；真实支付启用前核对后台配置与平台商品价格一致。第一版不额外扩展按模块、地区或年份拆售，也不实现任意规则引擎。

权益记录保留用户、范围、永久有效标识、发放时间、状态与来源。实现时以明确的永久类型及空到期时间表达，不使用很远的未来日期模拟永久；发放时间用于审计，不用于计算自然失效。来自不同订单/激活码的权益分别留痕；有效访问范围是所有当前有效来源的合并结果。每个来源最多产生一次对应权益发放。

永久权益取消原有期限起算、到期顺延和续期堆叠设计，Q02 不再因此阻塞实施。兑换后不能转移账号的规则保留。Q10 最新答复已确认禁止重复开通：用户已有同范围有效永久权益时，新购买及另一枚码兑换均返回“已激活”，不新建订单、不消耗新码、不新增兑换成功记录或重复发权益；新码保持原未使用状态。所有对应来源均已退款或撤销、该范围不再有有效权益时，才允许重新购买或使用另一枚未用且未禁用码开通。

原成功请求的超时重试与新开通请求分开处理：先校验用户归属、幂等标识和请求内容，已完成的同一原请求返回原订单／兑换结果及当前权益，不因为此时已激活而拒绝重试，也不重新消耗码或发放来源。请求内容改变或使用另一枚码不能借原幂等标识冒充重试；原权益随后被撤销时，返回历史结果不能重新激活该来源。

新增购买、兑换和权益确认发放须通过统一的用户与权益范围并发控制，在事务中重新校验授权、落库业务结果及必要唯一约束，不能只在进入页面时检查是否已激活。并发兑换不同码只能产生一次新开通，其余请求提示“已激活”且不消耗码；下单与兑换也必须防止检查后权益已改变仍创建重复业务。支付参数签发及支付成功确认阶段须再次核对一致性；已经发往平台的支付不能靠本地事务锁撤销。支付与兑换交错、迟到扣款和已付款冲突的状态及补偿流程在支付技术设计中明确，保留平台事实和审计，不静默吞款、不重复开通、不自设自动退款政策。

用户已明确允许管理员撤销误发且已兑换激活码对应的权益来源，永久不等于不可撤销。退款或误发撤销仅处理对应来源，不能清空该用户从其他订单或激活码获得的权益。在事务中标记目标来源已撤销并按其他有效来源重新判定授权：仍有同范围有效来源则继续享有永久权益；没有有效来源则仅保留免费访问范围。每次撤销保留来源明细、原因、操作人和前后授权结果，不删除订单、兑换及学习历史；不再进行期限扣减或区间重算。撤销权限已确认，无需再次等待业务答复。

## 7. 支付、订单与退款

### 7.1 官方支付路径与开通前提

本项目售卖的是题库访问等虚拟内容。依据本次调研，小程序支付方案应围绕官方虚拟支付 **`wx.requestVirtualPayment` 的道具直购（xpay）** 设计，不能默认使用普通 JSAPI/Native 收取题库费用。iOS 已有有条件支持能力，实际范围取决于主体、开通配置、渠道规则和客户端条件；不能写成“iOS 一律不能付”或“所有 iOS 均可直接支付”。参见 [微信小程序虚拟支付官方说明](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment.html)。

用户接受 Android/iOS 及 iOS 在小程序内使用 Apple 付款。最新旧账号后台截图显示企业主体已认证，但未备案；服务类目为信息查询、百货／超市／便利店及跑腿，搜索因涉嫌违规被限制；虚拟支付仍显示“开通”按钮，Apple 配置未展示。这些截图替代先前教育类目、认证备案完成的口述，不能将企业名称或普通商户号视作学习类目及虚拟支付能力的证明。处罚原因、恢复条件、适用类目及资质、备案与支付申请由甲方核实处理；后端基础开发可以推进，真实渠道验收仍需对应条件完成。实施时核对官方最新文档、该小程序虚拟支付签约/结算状态及 Apple 支付配置；后端通过能力状态和错误码拒绝未启用渠道，甲方前端据此展示，不偷偷切到其他收款方式。

我方支付交付包括服务端订单、调用参数准备、平台消息安全处理、查单补偿、退款事件与权益联动；甲方前端负责 `wx.requestVirtualPayment` 调用、支付页面和客户端状态查询。真实渠道尚未开通时保持关闭，不用固定成功返回、测试身份或模拟回调冒充真实交易能力。

查看开通状态的操作说明（根据 2026-10-02 核对的官方正文及[配置截图](https://res8.wxqcloud.qq.com.cn/wxdoc/620a320e-e255-4e65-b9a0-b70126f3b860.png)，用户后台菜单可能随版本调整）：

1. 登录[微信公众平台](https://mp.weixin.qq.com)，进入该小程序后台，查看左侧“支付与交易 → 虚拟支付”。
2. 若显示“开通”，说明仍需申请；若处于审核、账户验证、待签约等状态，开通尚未完成；显示“已签约”或已进入虚拟支付商户管理模块，再结合页面配置核对开通结果。
3. 在“虚拟支付 → 基本配置 → 基础配置”查看是否已有 OfferID；它是辅助核实信息，不能只凭页面出现某个字段判定全部支付链路可用。
4. 同页单独检查“是否启用苹果支付”开关。虚拟支付签约完成不代表 Apple 开关已经开启；正式接入还需按官方要求配置小程序简称等信息。
5. 反馈时只需告知页面状态和 Apple 开关状态，不需要在聊天或文档中发送 AppKey、AppSecret、密码或支付密钥。

### 7.2 试学与线上开通入口

Q04 最新答复确认线上购买无需扫码：用户免费试学后希望继续访问受限内容，甲方前端展示开通永久权益提示、商品信息和购买操作，再调用下单与官方支付能力。用户也可在试学完成前主动购买；不记录“已看完”作为允许下单条件，不规划线上二维码生成、扫码关联或跳转接口。

后端根据同一免费集合及有效永久权益决定内容访问。已有有效权益直接继续学习；无权请求只返回约定的授权状态和必要公开信息，不泄露完整付费内容。客户端提示、取消或按钮状态不能改变授权；成功付款后由服务端确认并发放永久权益。Q05 仍仅提供管理员 Web 后台，不增加学员电脑购买页；Q08 线下独立收款后管理员发码、小程序只兑换的流程另行保留。

### 7.3 下单与支付流程

1. 用户由试学开通提示或主动购买入口查看商品；下单前须登录，服务端在统一并发控制中校验已有同范围有效权益。有权益的新请求提示“已激活”且不新建订单；原成功请求的幂等重试返回既有结果。不要求先看完免费内容。
2. 服务端以商品配置生成订单和金额快照，校验客户端环境与可用支付渠道；客户端提交的金额不能作为收费依据。
3. 支付适配层按官方 xpay 规则准备支付信息，重新核对订单与当前权益状态并按第 6 节处理并发边界；仅向当前订单所属用户返回调用所需字段，不暴露服务端密钥。
4. 甲方前端调用官方支付能力。用户取消、调用失败或客户端回调成功都不直接改变最终权益。
5. 平台通知与服务端查单共同驱动订单确认；核对应用、渠道、订单、商品/金额及状态等必要信息。
6. 订单确认与权益发放通过统一并发控制、事务和唯一约束保证同一来源只发一次，避免与另一笔购买或兑换重复开通；已付款冲突按真实平台状态进入明确的核查及补偿流程，不以“已激活”提示丢弃交易。前端查询订单及权益，确认后进入学习。
7. 后端返回可查询及恢复的订单状态；甲方前端重开后可查询本人订单，不能因用户关页漏发权益。

内部金额建议按最小货币单位存储，支付适配时严格按该平台字段单位映射。xpay 的签名、商品标识和请求结构以官方协议为准，不能从普通微信支付 V3 参数照搬。

### 7.4 回调、查单与补偿

虚拟支付回调接入小程序消息推送，采用官方消息推送安全模式的校验、解密和响应要求；**不是普通微信支付 V3 的通知验签流程**。具体事件、重试与返回格式以 [微信消息推送官方说明](https://developers.weixin.qq.com/miniprogram/dev/framework/server-ability/message-push.html) 及虚拟支付文档为准，支付适配层负责隔离这些差异。

- 先校验消息来源与内容，再落库处理；保留必要事件标识和处理结果，敏感内容脱敏。
- 通知可能重复或乱序，查单也可能与通知同时发生；两条路径必须调用同一幂等“确认订单并发放权益”服务。
- 本地待支付不代表平台未扣款；超时、关单与迟到通知应查平台实际状态后处理。
- 已付款未发放、状态长期不明或消息处理失败进入待核查队列，可自动重试并供后台查看；重试仍不得重复发放。
- 不允许后台通过直接修改数据库状态伪造支付成功；运营修复须有核查依据和审计记录。

### 7.5 退款与撤销

Q11 已收到“开通后不退款、管理员处理”的经营要求；用户已补充允许管理员撤销误发且已兑换激活码对应的永久权益来源，并保留其他有效购买。异常交易处理时限及退款异常处理细节仍待明确。经营要求不等于可以忽略平台实际发生的退款，也不自动决定任何退款承诺的适用性。后台需保存核查、处理、平台执行结果与权益变化，区分处理中、成功和失败；不以人工备注代替平台结果。误发码权益撤销按第 8.4 节处理，不把该管理操作记成支付渠道退款。

普通虚拟支付可依据平台能力由开发者发起退款；Apple 支付由用户向 App Store 申请，开发者不能主动发起退款，后端需处理退款问询与退款完成推送。后台应按支付渠道显示对应的处理操作，不向全部订单提供同一种“发起退款”按钮。实际账户权限、接口条件与期限在接入时继续按[官方虚拟支付文档](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment.html)核验。人工处理也需要外部结果依据，不能把财务备注当作平台退款结果。

退款成功后按确认政策撤销或调整对应订单来源权益，并重新判定其他有效来源的授权；仍有有效来源保留永久权益，无有效来源回到免费范围。保存订单、退款、学习记录和审计历史。已退款订单的迟到支付通知不能再次激活权益；特殊争议状态需核查后处理。

## 8. 激活码生成、发放、兑换与管理

### 8.1 商业来源先确认

Q08 已确认管理员在后台生成激活码，用于免费赠送或独立线下收款后发放；小程序仅提供兑换，不展示线下收款码、联系购买入口或外部支付引导。这是已确认的经营流程，不表示平台已经批准其上线；实际交易与兑换页面仍需按当前平台规则核验。题库练习属于官方指南中的虚拟服务，不能仅凭“激活码”名称推断平台豁免。参见[微信虚拟支付业务运营指南](https://developers.weixin.qq.com/community/minihome/doc/00002cf077cd4810fee42f4b865c01)。

### 8.2 批次生成与保管

创建批次时选择已配置商品/权益、数量及业务备注。Q09 已确定单码单人一次，不需要机构标签，不设置兑换截止期限；未使用且未禁用的码可长期兑换。生成日期用于审计，不用于自动作废；不保留“一周后失效”的旧业务逻辑。最新答复另已确认兑换后发放永久题库权益；永久可兑换与永久学习权益分别记录，已兑换来源仍可按授权流程撤销。

使用密码学安全随机码，避免可预测流水号。Q09 不要求重复导出完整原码，生成时提供一次领取/导出机会，服务端持久保存校验摘要；展示和导出权限单独控制，审计记录不包含完整有效码。下载失败的恢复或作废重建应有明确提示，不增加长期明文保存和反复查看原码的入口。

批次、单码启用/禁用、导出和作废均记录操作人、对象、时间和理由。禁用未用码与撤销已经发放的权益是两个不同操作，界面必须说明影响。

### 8.3 兑换流程

已登录用户输入码 → 服务端规范化输入并限频 → 识别原成功请求的幂等重试 → 在统一用户与权益范围并发控制的数据库事务中校验授权、批次、码状态、剩余次数及对应权益 → 无有效权益时原子占用次数并发放同一来源永久权益 → 返回兑换结果与当前权益。已有同范围有效永久权益的新请求直接提示“已激活”，不消耗新码、不新增成功兑换或重复发权益；授权检查与码消耗不得分成可产生竞态的两步。永久码不做兑换截止时间检查；商品停止新销售时不能仅凭销售开关吞掉此前已发码的承诺，码的禁用与权益履约应分开处理。

请求需要幂等标识；并发使用同一码时只允许一次成功兑换。同一用户因超时重试应看到已完成的兑换结果，不能重复扣次数或发放。无效、已使用、禁用与暂时失败需有可理解提示，同时避免提供可被批量枚举的敏感信息；不向永久兑换码显示基于生成时间的“已过期”。

不允许转移账号；永久权益不再续期。禁止已有同范围有效永久权益的用户重复开通已由用户确认，执行规则见第 6 节；原成功请求的重试仍返回原结果及当前权益。已兑换误发码允许管理员按对应来源撤销永久权益，具体流程见第 8.4 节；所有对应来源失效且无有效权益后才可重新开通，已使用旧码不会因此恢复可兑。

### 8.4 误发已兑换码的权益撤销

这是用户已确认的后台能力。我方在 Django 管理后台提供独立授权的撤销操作，定位误发码、兑换记录、账户和该次永久权益来源；执行前展示撤销理由、当前来源明细及撤销后的授权影响，管理员确认后执行。

- 在同一事务中标记该来源已撤销、按其余有效来源重新判定授权，并记录操作人、时间、原因、目标来源和前后结果；仅影响误发码所贡献的权益，不删除其他订单或兑换记录。仍有同范围有效来源则保留永久权益，无有效来源则回到免费范围。
- 重复点击、超时重试及并发兑换／新购买不能二次撤销或覆盖新来源；同一撤销请求返回既有结果，最终权限以服务端重新判定的结果为准。
- 已兑换码保持已使用及关联撤销历史，不因撤权恢复为可再次兑换；学习记录和兑换历史保留。禁用未用码不等同于撤销已兑换来源。
- 对“只有误发来源”“另有正常购买／兑换来源”“目标来源已撤销或已退款”“撤销与新来源发放并发”分别验证，保证不侵占其他有效来源的永久授权。无需期限或续期算法，事务、唯一约束及重试幂等必须保证最终授权结果与有效来源一致。

## 9. 最小数据实体与一致性约束

以下是完整后端的数据边界；分类、篇目、题目/修订、后台权限与审计已有最小实现，其他业务实体为后续规划，并非已存在的表。按阶段只建立实际需要的模型，不为延期支付预建空模块。详细字段按接口契约及已确认规则确定。

| 实体 | 最少需要表达的信息 | 关键约束 |
| --- | --- | --- |
| 用户/微信身份 | 内部用户 ID、应用内微信身份关联、账户状态 | 同一应用身份唯一，不由客户端任意指定归属 |
| 分类/篇目 | 稳定 ID、来源、名称、排序、状态 | 被引用项不可直接物理删除；占位内容不正式发布 |
| 题目/修订 | 稳定 ID、关联、题型、题干、答案、标签、排序、版本 | 占位符合法；内容修改与 ID 分离 |
| 题库发布/导入记录 | 题目修订、改动摘要、结果、操作人、时间、错误行 | 发布原子生效，导入与发布分开；不预设全库版本表 |
| 用户题目状态 | 用户、题目、收藏、掌握、时间/版本 | 用户与题目组合唯一，设置状态可幂等重试 |
| 学习日/偏好/续学 | 学习日期、模式、学习上下文、有效题序及位置 | 学习日去重；账号隔离；上下文能验证有效性 |
| 随机练习轮次 | 用户、来源、题目/修订快照、固定题序、当前位置 | 一轮不重复，服务端控制可访问题 |
| 商品 | 售卖范围、价格、永久有效标识、状态、支付渠道映射 | 未启用或能力不足时禁止新下单；订单保存永久权益规则及价格快照 |
| 订单 | 用户、商品/价格快照、商户订单标识、状态 | 标识唯一，金额不可被客户端修改 |
| 支付/退款事件 | 渠道标识、外部记录、金额、状态、核查及处理结果 | 重复事件幂等，平台状态与内部状态可追溯 |
| 权益来源 | 用户、范围、永久类型、空到期时间、发放时间、来源类型/ID、状态、撤销记录 | 同一来源唯一发放；不以远期日期模拟永久；撤销后仍有有效来源则保留授权，否则回到免费范围 |
| 激活码批次/码 | 商品权益快照、生成及兑换时间、单次规则、状态、校验摘要 | 无兑换截止时间；码唯一、原子单次兑换、原码仅生成时领取 |
| 兑换记录 | 用户、码、请求标识、结果、关联权益 | 防并发超兑；请求重试返回同一结果 |
| 管理员/权限/审计 | 角色、操作人、对象、变更摘要、时间、结果 | 敏感操作必须服务端授权及留痕 |

内容状态、订单状态、退款状态和权益状态分开建模，不能用一个“已付款”布尔值承载全部流程。必要唯一约束应在数据库层落实，不能仅依赖“先查询再新增”的应用逻辑。

## 10. 后端 API 契约与甲方前端交接

以下是后续业务 API 的建议边界，用于 OpenAPI/接口说明定稿，尚未实现。实际已实现路径、字段与权限以《最小后端使用说明》为准；当前 `/api/v1/` 内容端点仍仅供后台 Session + 查看权限使用。下表以拟定的 `/api/student/v1/` 独立学员路径表达边界，保留现有管理员能力，不能以放开现有端点替代学员授权；该前缀在接口交接前统一定稿。所有路径沿用尾部斜杠约定。

我方交付请求与响应字段、认证方式、对象归属、分页及免费集合规则、状态与错误码、幂等和重试方式、时间与价格单位、接口版本兼容说明、示例及验收用例。示例响应标注为文档示例，不作为假业务返回。甲方前端依契约接入，我方提供接口问题定位与服务端修复支持。

- 对接时使用约定的测试数据、请求标识和脱敏日志定位问题。后端接口通过不代表甲方前端已验收；真实登录/支付须在甲方提供的环境和前端配合下另行核验，不承诺我方改造或原生联调交付历史小程序。

## 11. 权限、安全与运行保障

- 管理端权限在服务端校验，题库编辑、发布、退款、发放/撤销权益和原码导出分别授权。高影响操作显示具体对象及影响范围并记录审计。
- 小程序请求根据本站会话关联用户，所有订单、练习轮次、学习记录和兑换详情检查对象归属，防止通过改 ID 访问他人数据。
- API 与管理端使用 HTTPS；后台 Session 操作启用 CSRF 防护。敏感配置来自部署环境或受控密钥配置，不写入前端、仓库或普通日志。
- 激活码兑换、登录和下单设置可配置限频；文件上传验证类型和体积；题库富文本/媒体如启用需单独处理安全展示。
- 后端只向有权身份返回受限题目；向甲方前端交接“不将正式收费题库打包为公开资源、退出时清理敏感缓存”的接入约束。缓存实现由甲方负责，允许离线缓存的范围与时长须结合 Q15 和权益政策定义。
- 支付通知、查单和退款都记录必要证据与处理结果，日志脱敏。审计需要可保留和检索，不设置普通业务人员清空按钮。
- 数据库备份与恢复作为上线检查项；日志、导入文件、导出文件和历史记录的保留期限在运营配置中明确，不无限期堆积。
- 监测接口错误、异常登录/兑换、支付已确认但权益未发放、持续待核查订单、任务失败及备份失败。具体阈值依据运行情况设定，不编造当前负载。
